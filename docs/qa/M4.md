## Harness

Vom Repository-Root unter Windows:

```powershell
# Reiner Plan: keine Dienste, Browser, Profile oder Logs anlegen.
powershell -NoProfile -File .\scripts\dev-multiplayer.ps1 -PlanOnly
powershell -NoProfile -File .\scripts\dev-multiplayer.ps1 -PlanOnly -AsJson

# Lokale Dienste starten; Browserbefehle werden ausgegeben, nicht automatisch ausgeführt.
powershell -NoProfile -File .\scripts\dev-multiplayer.ps1

# Für die spätere manuelle Abnahme ausdrücklich drei eigene Browserprozesse öffnen.
powershell -NoProfile -File .\scripts\dev-multiplayer.ps1 -OpenBrowsers
# Optional: -Browser edge oder -BrowserPath 'C:\Pfad\zum\Browser.exe'

# Automatischer Start-/Stopp-Probelauf ohne Browser.
powershell -NoProfile -File .\scripts\dev-multiplayer.ps1 -StopAfterReady

# Ausschließlich Unit-/Widget-/Workerd-Gate, keine Browser-/E2E-Tests.
powershell -NoProfile -File .\scripts\test-multiplayer.ps1
```

Standard: Client `127.0.0.1:7357`, Worker `127.0.0.1:8787`, getrennte Profile A/B/C unter ignoriertem `.local/multiplayer/`. Der Client erhält getrennte API- und öffentliche Clientbasis. Alternativer Clientport ist 8080 (bereits erlaubte lokale Origin); der Workerport kann getrennt gewählt werden. Gleiche oder nicht erlaubte Ports werden vor einem Start abgelehnt. Kein LAN-/Cloudzugriff wird freigegeben; ein Handy-/LAN-Aufbau bleibt eine gesonderte spätere Einrichtung.

Die Harness besitzt ausschließlich ihre gestarteten Prozessobjekte. Dienste laufen verborgen mit getrennten lokalen Logs, Beenden erfolgt nur über deren konkrete PID samt Kindprozessbaum. Ctrl+C oder das Ende aller ausdrücklich gestarteten Browserprozesse beendet die eigenen Dienste. Fremde normale Browser-/IDE-/Node-Prozesse werden nicht nach Namen gesucht oder beendet. Profile werden niemals automatisch gelöscht; derselbe Pfad ermöglicht späteres gezieltes Fortsetzen. Eine exklusive lokale Sitzungssperre verhindert zwei gleichzeitige Harness-Instanzen. Ohne automatischen Browserstart bleiben die Dienste bis Ctrl+C aktiv, unabhängig von manuell gestarteten Fenstern.

## Später manuell durchführen

Profil A erstellt einen Raum; B tritt per Link und C per Code bei. B ändert Namen/Haare, A und C prüfen Figuren und Reihenfolge. Als Host einen Platz ändern und Entfernen abbrechen/bestätigen. In A einen Tab duplizieren und prüfen, dass die neuere Sitzung die ältere ablöst. Alle Fenster schließen, Harness neu starten und mit denselben Profilen dieselben Identitäten fortsetzen. Danach bewusst eine zusätzliche neue Identität beitreten lassen. Gesperrten Speicher, ungültigen/vollen/abgelaufenen Raum und Clipboardfehler nachvollziehen. QR mit Handy erst in einem ausdrücklich eingerichteten erreichbaren LAN-/HTTPS-Aufbau prüfen. Diese Schritte wurden nicht ausgeführt.

## Tatsächlich ausgeführt

115 Node-, 249 Flutter- und 125 Workerd-Tests grün. Drei neue Harness-Units prüfen Planbetrieb von fremdem CWD, isolierte persistente Profilpfade, Fenstergrößen, Port-/Optionskonflikte und getrennte Origins; PowerShell-Syntax und UTF-8-BOM geprüft. `dev-multiplayer.ps1 -StopAfterReady` startete die beiden echten lokalen Dienste, wartete auf HTTP 200 und beendete deren eigene Prozessbäume erfolgreich. Anschließend waren beide Ports wieder frei. Es wurde dabei kein Browser gestartet. Testprofile/Logs bleiben lokal ignoriert, keine Tokens in Plan oder Testbericht. Der Unit-Wrapper ersetzt gemäß Nutzervorgabe die geplanten neuen E2E-/Integrationsziele; bereits vorhandene alte E2E-Dateien bleiben erhalten und wurden nicht ausgeführt.
