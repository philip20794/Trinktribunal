# TT-035 – lokale Worker-/SQLite-Runtime

Stand: 27.10.2026. Nach ausdrücklicher Nutzervorgabe sind Browser-/E2E-Abnahmen **ÜBERSPRUNGEN – später manuell testen**; grüne Unit-Tests geben Folgeaufgaben frei. TT-035 implementiert die lokale Runtime, keine Raum-/Authentifizierungsfunktion vor TT-037/038.

## Ergebnis

- `apps/server` mit exakten DevDependencies und npm-Lockfile: Node 24.13.0 lokal, Wrangler 4.153.0, TypeScript 7.0.2, Vitest 5.0.5, Cloudflare-Vitest-Plugin 1.4.8, Node-Typen 24.19.2 und Prettier 3.9.10. Workerd 1.20261023.1, Kompatibilitätsdatum 2026-10-23. Die verwendeten Engines/Peer-Abhängigkeiten wurden im npm-Registry geprüft.
- SQLite-Durable-Object `Room` mit lokalem `ROOMS`-Binding und Migration `v1`. Kein Account, keine entfernten Bindings, kein Upload/Deploy; `workers_dev` und Telemetrie in der Konfiguration deaktiviert. Öffentliche Raumrouten bleiben geschlossen.
- `/health` liefert nur `{status:ok,service:trinktribunal,protocolVersion:1}`, JSON/no-store/nosniff, GET/HEAD; andere Methoden 405, unbekannte Pfade 404. Keine Identitäten, Credentials oder Raumzustände.
- `scripts/dev-server.ps1` startet die lokal gepinnte CLI auf Loopback, Standardport 8787, mit Vorbedingungen/Portprüfung/Exitcode und ohne globales Wrangler. Erstinstallation bei fehlenden Abhängigkeiten über `npm.cmd ci`.
- `scripts/check.ps1 -Scope Server` und `-Scope All` prüfen jetzt den tatsächlichen Server. `npm run check` umfasst Format, generierte Runtime-/Bindingtypen, Typecheck und Unit-Tests. Generierte Typen/Runtimezustand bleiben in ignoriertem `.wrangler`; Server-LF in Git festgelegt.
- Codemagic prüft zusätzlich das Server-Lockfile sowie die Server-Units vor dem APK-Build; kein Cloudflare-Deployment ergänzt.

## Ausgeführt

`npm.cmd ci --no-fund --no-audit` erfolgreich. `scripts/check.ps1 -Scope All`: 111 Node-/126 Flutter-/4 Server-Tests grün, Format/Analyze/Typecheck erfolgreich. Danach zusätzlich den im Workflow verlangten Server-Formatcheck eingebunden; `npm.cmd run check` einschließlich Prettier erneut grün. Die Server-Units laufen im echten lokalen Workerd-Kontext, nicht nur einem Node-Mock: Health, HEAD/405, 404 und SQLite-`SELECT 1` über das echte Durable-Object-Binding.

`scripts/dev-server.ps1 -Port 8787` erfolgreich gestartet: CLI meldet `env.ROOMS (Room) ... local`, Ready auf `127.0.0.1:8787`. `Invoke-RestMethod http://127.0.0.1:8787/health` liefert die erwartete JSON-Antwort, `/api/rooms` ergibt 404. Ein Browser wurde dazu nicht benötigt. Client-/Offline-/Androidquellen bleiben unverändert startbar; bestehende Flutter-Regressionen sind grün.

Unter Windows vor erneutem `npm ci` den laufenden lokalen Worker beenden: dessen esbuild-Prozess sperrt sonst die ausführbare Datei in `node_modules`. Nach Beenden nur dieses eigenen Dev-Prozessbaums wurde das endgültige Lockfile erneut erfolgreich mit `npm ci` installiert und Format/Typecheck/4 Runtime-Units grün geprüft. Der Probe-Devserver ist anschließend beendet; `.wrangler/state` bleibt als ignorierter lokaler Zustand erhalten.

Die Integration verwendet die aktuell dokumentierte Variante `@cloudflare/vitest-plugin`/`cloudflareTest`, nicht den älteren Pool-Konfigurationseinstieg. Quellen: [Cloudflare-Unit-Einstieg](https://developers.cloudflare.com/workers/testing/vitest-integration/write-your-first-test/), [Konfiguration](https://developers.cloudflare.com/workers/testing/vitest-integration/configuration/), [SQLite-Durable-Objects](https://developers.cloudflare.com/durable-objects/get-started/), [Prettier-CLI](https://prettier.io/docs/cli). Firecrawl war mit HTTP 402 nicht verfügbar; offizielle Dokumentation über den Webzugriff gelesen.

Nächste Aufgabe: TT-036 bindet strikte Dart-/TS-Decoder an die gemeinsamen Nachrichten-Fixtures. Echte Create/Join-/Token-/Socketfunktionen bleiben den dafür vorgesehenen Folgeaufgaben vorbehalten.
